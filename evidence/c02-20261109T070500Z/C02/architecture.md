## 1. Ringkasan Eksekutif & Batas Arsitektur Tetap (`Fixed Architecture Boundaries`)

Dokumen ini menetapkan arsitektur komponen, kontrak antarmuka logis, keputusan spesifik teknologi, dan rencana kelayakan kapasitas (*resource feasibility plan*) untuk **AI Agentic SRE & Hybrid RAG Investigation Engine — Scaled-Down Simulation PoC**.

Seluruh rancangan ini terikat pada **15 Batas Arsitektur Tetap** yang tidak dapat ditawar:
1. Seluruh layanan, transaksi, dokumen SOP, dan insiden bersifat **100% sintetis** (`RULE-001`).
2. Tidak ada infrastruktur bank nyata, kredensial korporat, atau data produksi (`NFR-012`, `NFR-017`).
3. Ekosistem terdiri atas **5 layanan mikro sintetis yang saling terhubung** (`api-gateway`, `auth-service`, `transaction-service`, `notification-service`, `db-dummy`) sesuai keputusan G0 `TBD-07` (melampaui syarat minimum $\ge 3$ layanan `FR-SIM-001` agar seluruh `SC-01`–`SC-14` didukung penuh).
4. Injeksi gangguan (*fault injection*) dikendalikan oleh *simulation harness* terpisah di luar jangkauan agent (`FR-SIM-004`, `RULE-003`).
5. Agent investigator hanya menerima *read-only tools* yang dibatasi skema dan waktu (`FR-AGT-002`, `FR-AGT-004`).
6. Tidak ada akses *shell*, *deployment*, *restart*, *write*, atau kueri database/PromQL/LogQL bebas dari investigator (`FR-AGT-003`, `MCP-01`, `KPI-09`).
7. *Ground truth* dan label *holdout* (`H-G3`, `H-G4`) sama sekali tidak dapat diakses oleh komponen runtime investigasi (`FR-SIM-005`, `RULE-002`, `AT-008`, `KPI-10`).
8. Pipeline retrieval menegakkan otorisasi layanan/environment dan masa berlaku dokumen (*applicability*) **sebelum** konteks dikirim ke model atau reranker (`FR-RAG-004`, `SEC-01`, `RAG-01`, `RAG-02`, `KPI-11`).
9. Isi log dan dokumen SOP diperlakukan sebagai **konten tidak tepercaya (*untrusted data*)**, bukan instruksi sistem (`RULE-004`, `SEC-02`, `AT-011`).
10. Sanitasi deterministik (`SEC-03`) wajib berjalan **sebelum** transmisi ke LLM, pembuatan embedding, pencatatan AI tracing, dan ekspor eksternal (`NFR-003`, `FAIL_CLOSED`).
11. Bukti yang hilang atau saling bertentangan menghasilkan status `PARTIAL` atau `INCONCLUSIVE`, bukan kepastian palsu atau bukti hasil rekayasa (`RULE-006`, `RULE-007`, `EV-01`, `EV-02`).
12. Review manusia (*human-in-the-loop*) wajib dilakukan untuk rekomendasi kritis dan penutupan dossier (`RULE-008`, `HUM-01`, `AT-010`).
13. Observabilitas AI (Langfuse/setara) **tidak** menggantikan rekaman audit keamanan independen yang bersifat *append-only* (`NFR-005`, `ADR-S06`).
14. Evaluasi dilakukan terhadap *ground truth* terisolasi **hanya setelah** output investigasi berstatus `CLOSED` (`FR-SIM-005`, `AT-014`).
15. Kelulusan Gate `G4` hanya membuktikan **kelayakan konsep (*concept feasibility*)**, bukan kesiapan produksi enterprise (`BRD §17`).

## 4. Keputusan Arsitektur Spesifik Teknologi (`Section 6 Requirements`)

### 4.1 Python + FastAPI untuk Layanan Simulasi (`ADR-S01`)
1. **Pola API & Identitas Layanan:**
   - Kelima layanan (`api-gateway`, `auth-service`, `transaction-service`, `notification-service`, `db-dummy`) dibangun menggunakan **Python 3.12** dan **FastAPI** (`CONFIRMED`).
   - Setiap layanan wajib mengekspos identitas kanonis melalui variabel lingkungan non-rahasia: `SERVICE_ID` (mis. `transaction-service`), `ENVIRONMENT` (`lab`), `BUILD_VERSION` (mis. `0.1.0-sim`), dan `INSTANCE_ID` (mis. `transaction-service-1`).
2. **Kontrak Health & Readiness:**
   - `/healthz` (*Liveness*): Mengembalikan HTTP `200 OK` dengan payload `{"status": "alive", "service_id": "...", "build_version": "..."}` selama proses Python responsif; **dilarang** memaparkan variabel lingkungan rahasia.
   - `/readyz` (*Readiness*): Memeriksa kesiapan dependensi lokal yang dibutuhkan kontrak layanan dan mengembalikan HTTP `200 OK` (`{"status": "ready", ...}`) atau HTTP `503 Service Unavailable` dengan `reason_code` terketik (`DEPENDENCY_UNREADY`, `POOL_EXHAUSTED`, `FAULT_INJECTED_UNAVAILABLE`). Kegagalan `/readyz` **bukan** izin bagi agent untuk melakukan `restart`.
3. **Envelope Error & Propagasi Telemetri:**
   - Seluruh error HTTP menggunakan envelope JSON standar (`error_code`, `message`, `service_id`, `environment`, `correlation_id`, `trace_id`, `timestamp`).
   - Middleware FastAPI secara otomatis mengekstrak atau membangkitkan header W3C `traceparent` (`00-<32hex-trace-id>-<16hex-span-id>-01`) dan `X-Correlation-ID` pada pintu masuk `api-gateway` serta meneruskannya ke seluruh panggilan `httpx` hilir dan event antrean lokal.
4. **Disiplin Ketergantungan Runtime:**
   - Tidak ada penambahan message broker eksternal berat (seperti Kafka/RabbitMQ) atau RDBMS terpisah untuk layanan simulasi tanpa ADR baru; `db-dummy` dan antrean `notification-service` diimplementasikan menggunakan FastAPI + penyimpanan ringan terkendali (`SQLite` / bounded in-memory state dengan hook latensi dan batas pool) agar 100% deterministik dan hemat RAM.

### 4.2 Observability: Prometheus + Loki + Tempo + Grafana (`ADR-S02`)
1. **Peran Sistem Rekaman (*System of Record*) vs Visualisasi:**
   - **Prometheus** (metrics), **Loki** (logs), **Tempo** (traces), dan **Service Catalog** adalah *telemetry systems of record* untuk lab simulasi.
   - **Grafana** berfungsi **murni sebagai lapisan visualisasi manusia**; agent investigator **tidak pernah** membaca dashboard Grafana atau memanggil API Grafana.
2. **Pipeline Koleksi Minimum:**
   - Layanan FastAPI mengekspor metrik Prometheus (`/metrics`), menulis structured JSON logs ke `stdout` (dikumpulkan menuju Loki dengan label rendah kardinalitas: `service_id`, `environment`, `severity`), dan mengirim span OTLP ke Tempo (melalui OTel Collector ringan atau eksportir OTLP langsung).
3. **Kontrak Kueri Terikat, Timestamp, & Perilaku Saat Backend Hilang (`EV-02`):**
   - Kueri dari MCP Gateway ke Prometheus, Loki, dan Tempo **wajib** menggunakan template berparameter dengan batas `start`, `end`, `max_points`/`max_hits`, dan timeout ketat.
   - Waktu peristiwa asli (*source event/sample timestamp*) dibedakan secara eksplisit dari waktu pengambilan oleh gateway (`observed_at`).
   - Jika Tempo (atau Prometheus/Loki) dimatikan atau mengalami timeout (skenario `SC-09` / `EV-02`), adapter **wajib** mengembalikan `status="unavailable"`, `data_quality="unavailable"`, `records=[]`, dan `error_code="SOURCE_UNAVAILABLE"`. Dilarang keras mengubah sumber mati menjadi angka `0` atau mengarang span trace palsu.

### 4.3 Hybrid RAG: Qdrant-Native Dense + Sparse (`ADR-S04`, `TBD-06`)
1. **Arah Arsitektur Terpilih:**
   - Menggunakan **Qdrant-native Hybrid Search** yang menyimpan *named dense vector* dan *named sparse vector* di dalam koleksi Qdrant yang sama (`SELECTED APPROACH`). Pendekatan ini menghilangkan kebutuhan menjalankan klaster Elasticsearch terpisah di dalam batas 8 GiB RAM.
2. **Identitas Dokumen, Siklus Hidup, & Otorisasi Pra-Konteks:**
   - Setiap chunk wajib memiliki metadata kanonis (`chunk_id`, `document_id`, `document_version`, `index_version`, `service_id`, `service.name`, `environment`, `status`, `effective_from`, `effective_to`, `classification`, `allowed_groups`, `content_hash`).
   - Filter otorisasi (`service_id`, `environment`, `allowed_groups`) dan filter siklus hidup (`status == "approved"` serta `effective_from <= incident_reference_time < effective_to`) diterapkan sebagai **mandatory Qdrant payload pre-filter** pada **semua** cabang pencarian (*dense-only*, *sparse-only*, dan *hybrid*) **sebelum** skor digabungkan dan **sebelum** konten menyentuh reranker atau LLM (`SEC-01`, `RAG-01`, `RAG-02`).
3. **Pemeliharaan Baseline & Evaluasi Objektif:**
   - Walaupun arsitektur target menggunakan kueri hybrid (Reciprocal Rank Fusion / `RRF`), layanan retrieval wajib menyediakan parameter `ranking_mode` (`lexical_only`, `dense_only`, `hybrid_rrf`, `hybrid_rerank`) agar evaluasi komparatif `AT-006` / `KPI-05` dapat membuktikan secara objektif apakah hybrid benar-benar mengungguli *dense-only* dan *sparse-only* pada korpus yang sama.
4. **Semantik Penghapusan, Reindexing, & Version Fencing (`FR-RAG-008`):**
   - Pembaruan korpus menggunakan mekanisme *collection alias / index version fence* (`index_version`). Dokumen yang dicabut (`withdrawn`) atau digantikan (`obsolete`) segera kehilangan kelayakan sitasi aktif, dan cache retrieval di-invalidasi berdasarkan `index_version`.

### 4.4 Dify-First Orchestration & Evaluasi Kapabilitas (`TBD-05`, `ADR-S01`)
1. **Status Kandidat:**
   - **Dify Self-Hosted** diperlakukan sebagai **kandidat utama (*Dify-first candidate*)**, **bukan** mesin workflow final yang diasumsikan otomatis lulus.
2. **Sepuluh Kriteria Evaluasi Wajib pada Spike `C08`:**
   - Rencana pengujian kapabilitas (`plans/c08-orchestrator-spike.md`) menguji Dify terhadap: (1) *Durable state*, (2) *Idempotency*, (3) *Retry & backoff*, (4) *Timeout & cancellation*, (5) *Tool allowlist & server-side authorization*, (6) *Independent auditability*, (7) *Evidence provenance preservation*, (8) *Deterministic replay*, (9) *Human review handoff*, dan (10) *Failure recovery* — ditambah kecocokan memori di dalam plafon **8 GiB RAM** bersama 5 layanan + observability + Qdrant.
3. **Arsitektur Alternatif & Tenggat Keputusan:**
   - Jika pada spike `C08` Dify terbukti melampaui anggaran memori 8 GiB RAM atau tidak mampu menegakkan *deterministic policy/idempotent replay* di luar prompt, maka arsitektur beralih secara terkendali ke **Pola B (Hybrid External Python Coordinator + Dify Reasoning Node)** atau **Pola C (Pure Python Deterministic State Machine / LangGraph dengan SQLite WAL State Store)** yang mengimplementasikan kontrak `workflow-event.v1.schema.json` yang sama persis. Keputusan final dikunci pada **Chapter `C08` (Gate `G1`)**.

### 4.5 Strategi LLM Hybrid (`TBD-04`, `ADR-S06`)
1. **Urutan Rute Provider-Independen (`Confirmed Policy`):**
   $$\text{Route 1: Remote Free-Tier LLM API} \xrightarrow{\text{on error / timeout / quota}} \text{Route 2: Local Model Fallback (Ollama } \le\text{3B)} \xrightarrow{\text{on dual failure}} \text{Route 3: Deterministic Evidence-Only Manual Fallback}$$
2. **Sembilan Kriteria Seleksi Provider & Model:**
   - (1) Akses `$0.00` terverifikasi tanpa tagihan otomatis (*zero-cost access*); (2) Kapabilitas output JSON terstruktur & kepatuhan skema; (3) Kuota RPM/RPD/TPM yang memadai untuk batch replay; (4) Kebijakan retensi & *no-training* didokumentasikan; (5) Hanya menerima data sintetis yang telah lulus redactor `SEC-03`; (6) Latensi mendukung target P95 $\le 120\text{ s}$; (7) Penanganan error HTTP `429`/`5xx`/timeout yang deterministik; (8) Keterlacakan `model_id` & `provider_version` di setiap dossier; (9) Kompatibilitas model fallback lokal dengan Apple Silicon `arm64` dan memori 16 GB.
3. **Perilaku Saat Kedua Rute Model Gagal (`OPS-02`, `AT-012`):**
   - Jika rute remote dan rute lokal gagal/timeout, sistem **tidak boleh** mengarang hipotesis atau menghapus bukti yang sudah terkumpul. Coordinator beralih ke **Route 3 (Controlled Deterministic / Manual Fallback)**: merakit dossier berstatus `INCONCLUSIVE` (dengan `error_code="LLM_UNAVAILABLE"`), melampirkan seluruh bukti telemetri dan SOP yang berhasil diambil pada tahap sebelumnya, menulis event ke `Independent Security Audit Store`, dan menyerahkannya ke antrean `HUMAN_REVIEW`.

### 5.3 Total Anggaran Memori Gabungan & Strategi Graceful Degradation

1. **Konfigurasi Operasional Standar (Profil `1 + 2 + 3 + 4 [Ringan]` + Remote Free-Tier LLM):**
   $$\text{Total Estimasi RAM} \approx 550\text{ MiB} + 1,150\text{ MiB} + 650\text{ MiB} + 300\text{ MiB} = \mathbf{2,650\text{ MiB } (\sim 2.59\text{ GiB})} \ll 8.0\text{ GiB Cap}$$
   Konfigurasi ini menyisakan ruang kepala (*headroom*) **>5.4 GiB** di dalam plafon 8 GiB lab, sehingga sangat aman bahkan saat model fallback lokal `<=3B` (~`2.0 GiB`) dimuat sementara (total puncak ~`4.65 GiB` $\le 8.0\text{ GiB}$).
2. **Konfigurasi Saat Spike Dify (`C08`):**
   - Jika Dify (~`3.0–4.0 GiB`) diuji bersama Profil `1 + 2 + 3` (~`2.35 GiB`), total memori mencapai ~`5.35–6.35 GiB` (masih muat untuk uji fungsional dengan Remote LLM, namun **rawan melampaui 8 GiB** jika digabung bersamaan dengan `Ollama <=3B` lokal dan `Langfuse` self-hosted).
   - Oleh sebab itu, pada `C08` wajib diuji apakah Dify dapat dijalankan dalam profil *minimal worker* tanpa kontainer UI berat, atau apakah orkestrasi state dieksekusi oleh *Lightweight Python Coordinator* agar plafon 8 GiB tidak pernah dilanggar.
3. **Urutan Startup (`Startup Sequence`):**
   - Tahap 1: Nyalakan `observability` (`prometheus`, `loki`, `tempo`) $\rightarrow$ tunggu `/ready`.
   - Tahap 2: Nyalakan `core-sim` (`db-dummy` $\rightarrow$ `auth-service` & `notification-service` $\rightarrow$ `transaction-service` $\rightarrow$ `api-gateway`) $\rightarrow$ verifikasi `/healthz` dan `/readyz`.
   - Tahap 3: Nyalakan `rag` (`qdrant` $\rightarrow$ `rag-gateway-service`) $\rightarrow$ verifikasi `index_version`.
   - Tahap 4: Nyalakan `orchestration` (`mcp-policy-gateway` $\rightarrow$ `coordinator` / `intake`).
4. **Prosedur Stop, Reset, & Graceful Degradation:**
   - **Stop/Reset Antarskenario:** Hentikan trafik $\rightarrow$ panggil `fault-harness reset` $\rightarrow$ bersihkan state sementara `db-dummy`/queue $\rightarrow$ verifikasi `/readyz` 5 layanan kembali sehat tanpa menghapus ledger `Independent Security Audit Store` atau `Restricted GT Registry`.
   - **Graceful Degradation saat Tekanan Memori (>7.2 GiB dari 8 GiB Cap):**
     1. Matikan kontainer visualisasi `grafana` (mode headless; menghemat ~`150–250 MiB`).
     2. Set `OLLAMA_KEEP_ALIVE=0` agar bobot model lokal segera dilepas dari RAM begitu inferensi fallback selesai.
     3. Gunakan model fallback lokal `1.5B` Q4 (~`1.1 GiB`) alih-alih `3B` Q4 (~`2.2 GiB`).
     4. Jika tetap jenuh pada uji stres konkurensi tinggi (`C20`), hentikan penambahan beban dan catat sebagai `CAPACITY_CEILING_REACHED` sesuai `budget-and-schedule.md` §3.
